One product system, not a collection of parts.

SerotoniX™ is being developed as an integrated wearable platform. Fit, stimulation, sensing, software, power, communication and evidence control must work as one managed configuration.

System architecture

The difficult work sits at the interfaces.

A wearable can fail even when each component works in isolation.

Contact consistency, fit, electrical output, feedback, charging, cleaning, software state and user comprehension interact. The design programme therefore treats the shell, electrode interface and controller as one risk-managed system.

01

Personalised interface

Geometry, materials, ventilation, strap management, contact placement and repeatable donning.

02

Controlled output

Channel configuration, charge balance, output limits, contact monitoring and fault response.

03

Control and data

Session configuration, device state, feedback, logging, power and communications.

04

Evidence control

Every test result must identify the exact hardware, firmware, interface and protocol version.

Meaning of personalisation

Personalised must be measurable.

The term should describe controlled adaptations, not vague individualisation. Candidate variables include geometry, strap setting, contact map, permitted session configuration and software guidance. Each variable needs limits, verification and a record of what changed.

A

What can vary

Fit, placement, interface components, guided setup and bounded configuration.

B

What must remain controlled

Safety limits, component compatibility, software logic, traceability and test acceptance criteria.

Quiet bottlenecks

The programme succeeds or fails on repeatability.

The central engineering risk is not whether a prototype can produce an output once. It is whether intended users can obtain the intended fit and session repeatedly, under realistic conditions, without creating unacceptable risk.

Fit

Can users position and secure the interface consistently across sessions?

Contact

Can the system detect poor or changing contact before output becomes unreliable?

State

Can the user understand readiness, active operation, faults, completion and charging?

Recovery

Does the system fail safely and guide the user back to a known state?
